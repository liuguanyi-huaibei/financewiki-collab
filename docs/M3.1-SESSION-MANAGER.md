It has not been installed into the live Vault. The development branch manifest is marked 0.3.0-dev.1 to distinguish its build from the immutable 0.2.3 release.

## 1. Goal

Upgrade the v0.2.3 single-test-note MVP into a workspace that can safely manage several collaborative Markdown documents at the same time. This milestone is about document/session lifecycle and identity; it is not yet full Vault synchronization.

## 2. v0.2.3 implementation facts

- FinanceWikiCollaborationPlugin owns sessions: Map<roomId, CollaborationSession> and editorViews: Map<filePath, Set<EditorView>>.
- getOrCreateSession(file) derives roomId from workspaceId + file.path, creates a Y.Doc, IndexedDB persistence and WebrtcProvider, then stores it in the plugin map.
- createIndexedDbName(roomId) derives the IndexedDB name from the room ID.
- Each editor view currently attaches to the room session; the view plugin unregisters the editor view when destroyed.
- The plugin unload path destroys every session, but normal editor-view release does not yet decrement a session reference count or schedule idle cleanup.
- The current identity is path-derived. Renaming or moving a file changes its room ID and IndexedDB name; the old room remains separate.
- The current code can hold more than one room in the map, but a formal multi-document lifecycle, bounded resource policy and rename/move continuity are not yet implemented or accepted.

## 3. Compatibility invariants

M3.1 must preserve these invariants unless a separately reviewed migration is introduced:

1. Existing v0.2.3 room IDs remain unchanged.
2. Existing IndexedDB names remain unchanged; never delete or clear a database as part of session acquisition/release.
3. Existing Workspace ID, collaboration-folder setting, signaling URLs and room password remain unchanged.
4. Never auto-seed an existing document. Seeding remains an explicit, guarded operation.
5. A failed session open must not unlock a collaborative editor before local IndexedDB state has loaded.
6. Destroying one document session must not disconnect another document's provider or shared signaling socket.
7. Reopening a document while its prior session is being released must not create two live providers for the same identity.

## 4. Target architecture

    FinanceWikiCollaborationPlugin
      ├── EditorBindingController

      │     └── acquire/release session lease
      ├── DocumentRegistry

      │     ├── legacyRoomId / persistenceKey compatibility
      │     └── registry schema version
      └── SessionManager
            ├── sessionsByDocumentId
            ├── sessionsByRoomId
            ├── reference counts / editor leases

                        ├── WebrtcProvider

The editor binding layer must not construct or destroy Y.Doc, persistence or providers directly. It requests a lease from SessionManager and releases that lease when the CodeMirror view is destroyed.

## 5. Identity and registry design

### 5.1 Separate document identity from transport identity

The target descriptor is:

    interface DocumentIdentity {
      documentId: string;       // stable workspace-scoped logical identity
      workspaceId: string;
      currentPath: string;      // normalized Vault-relative path
      roomId: string;           // transport identity used by y-webrtc
      persistenceKey: string;   // IndexedDB key
      identityVersion: 1;
    }

documentId must not be treated as interchangeable with roomId or persistenceKey. The latter two are compatibility-sensitive in v0.2.3.

### 5.2 Backward-compatible bootstrap

For every existing path-based v0.2.3 note, bootstrap a registry record with:

- a deterministic workspace-scoped document ID derived from normalized workspaceId + path;
- the exact existing createRoomId(workspaceId, path) as roomId;
- the exact existing createIndexedDbName(roomId) as persistenceKey.

This is an identity index, not a Yjs content migration. It must not copy, rename, delete or reinitialize existing IndexedDB databases.

### 5.3 Shared registry

The registry is workspace-scoped and eventually replicated as a dedicated Yjs document in a reserved room, with its own IndexedDB persistence. Its schema should include:

- schema version;
- document records keyed by documentId;
- current path index;
- lifecycle state (active / tombstoned);
- creation/update metadata and operation IDs for conflict diagnostics.

The reserved registry room name must be distinct from all file rooms. Registry initialization is automatic and idempotent; it must not reuse the user-facing document Seed command.

### 5.4 Rename/move policy

Do not silently derive a new roomId after rename/move. A rename operation must preserve documentId, roomId and persistenceKey, and update the registry path mapping. Concurrent path collisions or conflicting moves must be surfaced as conflicts, not resolved by overwriting document content. Full rename/move automation is a later sub-phase after the registry has dual-device tests.

### 5.5 Deletion policy

Deletion is not equivalent to session release. Releasing the last editor lease may evict an idle in-memory session but must never delete IndexedDB or registry records. File deletion/tombstoning and garbage collection are deferred until explicit retention and restore rules are designed.

## 6. SessionManager API contract

Initial interface target:

    interface SessionLease {
      readonly identity: DocumentIdentity;
      readonly session: CollaborationSession;
      release(): Promise<void>; // idempotent
    }

    interface SessionManager {
      acquire(identity: DocumentIdentity): Promise<SessionLease>;
      getByDocumentId(documentId: string): CollaborationSession | undefined;
      getByRoomId(roomId: string): CollaborationSession | undefined;
      list(): readonly CollaborationSession[];
      closeAll(): Promise<void>;
    }

Implementation requirements:

- Concurrent acquire() calls for the same document must share one creation promise.
- Each acquired editor view gets an idempotent lease; releasing one view must not close a session still used by another view.
- After the final lease is released, an idle grace period may be used before eviction. Reacquisition during that period cancels eviction.
- closeAll() must stop retry managers, disconnect/destroy providers, await persistence destruction and destroy Y.Docs exactly once.
- Creation/destruction races must be serialized per document identity.
- Expose session lifecycle state for diagnostics: creating, loading-local, ready, connecting, connected, idle, closing, error.
- Resource limits must be explicit and configurable; never evict a session with active leases.

## 8. Acceptance criteria

1. At least five distinct Markdown notes can be opened concurrently without room or content cross-talk.
2. Two devices can edit the same note and different notes concurrently.
3. Multiple editor views of one file share one Y.Doc/provider/persistence instance.
4. Closing one split-pane view does not tear down another view's active session.
5. Closing the last view eventually releases in-memory resources without deleting IndexedDB.
6. Reopening during the idle grace period reuses the same session; reopening after eviction restores the same persisted state.
7. Plugin unload closes all sessions and leaves no provider, awareness listener or IndexedDB observer alive.
8. Existing v0.2.3 test notes reconnect using their original room IDs and IndexedDB names.
9. Tests cover concurrent acquisition, release/destruction races and failed local persistence.
10. No data migration is enabled until dual-device compatibility tests pass.

## 9. Out of scope for M3.1

- General file-tree synchronization and automatic remote file creation.
- YAML Frontmatter synchronization and metadata conflict policy.
- Attachment transfer.
- Team membership, authentication and ACLs.
- Public Internet NAT traversal/TURN deployment.
- Deleting or garbage-collecting persisted document data.

## 10. First implementation task

Start with M3.1-A only. Keep v0.2.3 tagged and immutable. Implement SessionManager behind the existing room IDs, then migrate the editor binding and diagnostics. Run npm run validate and add lifecycle tests before any M3.1 code is installed into the live Obsidian Vault.
